# 並列開発の運用

統括だけが子を起動する。子からの再委任は設定で禁止する。
エージェント数に固定の総上限は設けないが、APIの制限・CPU・メモリ・競合は別問題として扱う。
初回は独立した2～4件で開始し、待ち時間・メモリ・失敗率を見て増やす。
無制限の利用可否や将来のサービス仕様を前提にしない。

## 作業票

統括はdocs/WORK_QUEUE.mdに担当を記入してから次の情報を子へ渡す。

```text
ID / 目的:
基準HEAD / 既存差分:
依存タスク:
編集可能なファイル（具体的に）:
読むべきコード・仕様（必要な箇所だけ）:
期待する動作 / 受け入れ条件:
実行可能なテスト / ログ保存先:
共有資源の使用可否:
返却形式: 変更ファイル、挙動、コマンド/終了値/証拠、未解決事項
```

- 同一ファイルの書き手は一人。共有STATE・作業キュー・公開資料の最終更新は統括だけ。
- 同じagentを複数起動しても担当IDとファイルを分ける。
- 同じcheckoutではgit checkout/reset/clean/stash/commitを子に行わせない。
- 大きく競合する変更は統括がworktreeを用意する。未コミット変更は自動で移らない。
  別worktreeを用意するだけで同一基準になったと考えず、必要な変更を明示的に引き継ぐ。
- 子はMozc submoduleを直接編集しない。pinned sourceへのpatch/overlayを変更する。
- 調査・レビューは並列化できる。Bazel/MSVC、同一Cargo target、stage/packageは
  `scripts/with-development-lock.ps1 -Name build` で一件ずつ実行する。
- 実機インストール/登録/アンインストールは `-Name machine` で一人が扱う。
  インストール対象と現在の入力設定を記録する。
- ロックを使わない外部プロセスまでは防止できない。開始前に既存ビルド・OpenCodeの編集を確認する。
- 待ち合わせ中に同じビルドを複製しない。基準ソースが変わった検証は無効範囲を明示する。
- 子の失敗後はログを一度読み、仮説を変える。同じ失敗を別の子に丸投げし続けない。

## 受け入れと次のバッチ

統括は差分確認 → 必要な独立レビュー → 対象テスト → 統合テストの順に受け入れる。
重い統合テストは互換性のある変更をまとめた固定状態で一度実行する。
未検証の変更をPASSにしない。verifier実行中は対象ソースを凍結する。
子の長い会話は転記せず、再現に必要な証拠と次の一手をSTATE冒頭へ残す。

権限ルールは誤操作を減らす補助であり、shell経由の書き込みを完全隔離するsandboxではない。
tester/verifierのshellをソース編集や権限制限の迂回に使わない。
