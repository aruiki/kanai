PRODUCT BOUNDARY

まず「何を作らないか」を決めた

KanaAIはWindowsの日本語IME（入力方式）です。チャット画面、ブラウザの作業台、CLIツールは製品ではありません。開発中にそれらを作りましたが、製品の出荷単位はTSFに対応したネイティブIMEであると境界を引き直しました。

この境界は装飾ではなく、実装の優先順位を決めます。「AIと会話して文章を作る」機能より、「打った文字が正しく候補になり、確定できる」ことが常に勝ちます。

境界の不変条件

AIは変換の依存要素にしてはいけない。AIが応答しなくても、候補は出て、文字は確定できる。生成AIはユーザーが呼び出し、中止でき、結果を事前に確認でき、変換の前提にならない。

WHY MOZC

Mozcを再実装しない理由

日本語入力の難しさの大半はAIではなく、辞書・形態素解析・変換・候補生成・学習・OS統合にあります。これらはMozcが長い期間かけて作り込んでおり、理由なく書き直すのは品質を落とすだけの作業です。

Mozcから使うものKanaAIが足すもの
かな漢字変換、形態素解析、候補生成候補の並び替え・方針決定の層（制限時間つき）
システム辞書、ユーザー辞書、学習文脈の管理と、個人適応の記録
履歴、OS統合、TIP（Text Services Framework）ローカル推論との接続、プライバシー方針

MozcのコードはBSD-3-Clause、辞書データと一部サードパーティは別の条件が混在します。KanaAIは同梱ライセンスをそのまま保持し、1つのライセンスであると仮定しません。

Google 日本語入力の独自コード、辞書、クラウドデータ、UIは複製していません。品質の基準として「成熟した日本語IMEの体験」を置きますが、比較は固定したMozcベースラインに対して再現可能な日本語ケースで行います。

LANGUAGE SPLIT

C++ / Rust / TypeScript の分担

層言語理由
変換エンジン・TIPC++（Mozc）既存の実装とWindows統合がそのまま使える。移植には測定結果か具体的な保守上の理由が必要。
並び替え、文脈、キャッシュ、個人適応、推論連携、ネイティブ境界Rust新規に書く部分。メモリ安全と、IMEプロセスから分離できる境界の明確さ。
説明用のラボUITypeScript開発専用。ループバックで動き、本番の入力やプロファイルデータを既定では読めない。署名された配布物には含めない。

「Rustで書き直せば速くなる」は主張しません。既存C++の移植は、測定結果または具体的な保守上の理由があるときだけ行います。

FAST PATH / SLOW PATH

キー入力の同期経路に、重いものを置かない

経路を2つに分けました。分けなかった場合、モデルの起動やディスク読み込みが打鍵のたびに起き、入力が止まります。

Fast PathSlow Path
いつ打鍵ごと（同期）確定後（非同期）
何をMozc変換＋軽量な並び替え・方針決定確定した文章と、許可された短い文脈の処理
禁止大型モデル、ディスクI/O、通信未確定入力からの学習
失敗したらMozcの候補をそのまま返す結果を捨てて次へ

さらに、世代の古い結果と候補IDの改変を拒否します。入力が進んだあとに届いた推論結果は捨て、AIが候補の識別子を書き換えることも許可しません。

FAILURE HANDLING

AIが落ちても、入力は止まらない

AIの未起動、タイムアウト、クラッシュのいずれでもMozc入力を維持します。これは目標ではなく出荷条件です。

  • 鍵ストアが無い、ネットワークが切れた、プロバイダが使えない、同期が無効 —— いずれの場合も平文へのフォールバックは起きません（fail-closed）。
  • パスワード欄などの保護フィールドでは、文脈の取得・AI・学習を停止します。
  • 診断ログは設定値・パス・入力テキスト・トークンを含みません。

LOCAL AI IN PRACTICE

ローカルAIを実際に動かして分かったこと

同梱AIは完全オフラインです。実行環境は 127.0.0.1（ループバック）だけで待ち受け、プロセスごとの鍵で保護されます。テキストがこのPCの外へ出ることはありません。起動時には同梱バイトのハッシュを検証します。

低整合性プロセスという落とし穴

beta.2 の開発で、AIのコードもモデルも動くのに製品経路では一度も起動しない状態に当たりました。原因は権限ではなく整合性レベルです。

起動元子プロセスメモリ
mozc_server（低整合性）conhost のみ — AIなし7 MB
powershell（中整合性）conhost + llama-server1,664 MB

同じバイナリ・同じPC・同じアカウントで、違いは親プロセスだけでした。MozcはIMEサーバーを低整合性で動かし、そこから起動されるプロセスも継承します。低整合性プロセスは %TEMP% にディレクトリを作れず、鍵の準備に失敗してAI経路が放棄されていました。

さらに深刻だったのは、理由がどこにも残らなかったことです。テキストサービスはコンソールもリダイレクト先も与えないため、診断はすべて捨てられ、外からは「設計どおりAIが無効」と「起動に失敗した」が区別できませんでした。

修正は、鍵の置き場所の候補に低整合性向けの AppData\LocalLow\KanaAI を追加し（%TEMP% が第1候補のままなので通常の挙動は不変）、起動診断を broker-startup.log に記録し、書けなければ LocalLow へフォールバックする、の2点です。鍵ファイルの保護は弱めていません。

MEASURED, THEN REJECTED

6つの役割を測って、全部ダメだった

同梱モデル（Qwen2.5-1.5B-Instruct Q4_K_M）に与えうる役割を、実物の実行環境に実物のプロンプト機構経由で聞いて測定しました。結果は次のとおりで、1つも採用できませんでした。

役割実測判定
候補の並び替えtop-1 が 6件中 0件不採用
かな→漢字変換完全一致 12件中 2件不採用
読み生成（ふりがな）完全一致 15件中 5件出荷不可
誤りの指摘（ヒントとして）8件中5件検出、誤検出2件出荷不可
誤りの位置特定5件中 0件不採用
Slow Path の節補完6件中 3件が空、1件は再現せず出荷不可

失敗のしかたは漠然としていません。変換では、当てずっぽうではなく入力のかなや前後の文脈をそのまま返すのが主な失敗（12件中7件）でした。答えの形だけを整えて、変換をしていません。

そして、採用の判定に使っていた自己申告の confidence は正しさについて何も情報を含んでいませんでした — 0.9 はすべての誤答に付き、正答には付きませんでした。

これは何の主張で、何の主張ではないか

これは重みについての記述であって、配管についての記述ではありません。供給経路は固定され、実行環境は埋め込みの起動計画から立ち上がり、モデルは固定バイトから読み込まれ、すべてのプロンプトに答えます。ローカルモデル一般や llama.cpp についての記述でもなく、別の重みがどう動くかを予測するものでもありません。

この6つの測定は crates/kanai-broker/tests/ai_decision_probe.rs にゲートつきテストとして書いてあります。KANAI_AI_EVIDENCE=1 を設定しない限り KANAI_AI_EVIDENCE=NOT-PERFORMED を出力するので、新しいモデルは同じ計器で測られます。新しい議論では測りません。

MODEL LADDER

モデルは「積む」のではなく「選ぶ」

実行クラス想定モデル用途メモリ目標
MozcOnlyなし変換、候補生成、ローカル学習0–256 MiB
FastRanker小型分類器／埋め込み候補の特徴スコアリング<1 GiB
Tiny0.6B Q4 級短い曖昧性・修正プロンプト1–2 GiB
Compact1.7B Q4 級意味的な並び替え・明示的な書き換え2–4 GiB
Balanced4B Q4 級長文の明示的な支援4–6 GiB

推奨クラスは空きメモリと使える加速器の余裕から決めます。搭載VRAMだけでは決めません。余裕がなければ MozcOnly が正しい答えです。
